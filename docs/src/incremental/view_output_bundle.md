# 视图结果与输出变更日志合并持久化

**状态**　已按项目负责人的评审意见确定（`accepted`）。2026-11-28。

**基线**　`1486d3b`。适用于本地 SQL 数据库存储的自动提交和显式事务。

## 1. 目的与证据

本地 TPC-H Q6 的 92 对普通提交中，启用视图后平均多用 6.46 ms。其中写新结果块平均 2.82 ms，写带符号的输出变更日志平均 2.67 ms。这两个文件分别调用一次 `sync_all`，调用内共用 4.90 ms。目标是在同一次提交内把同一视图的新结果数据和输出日志放进一个不可变文件，整个文件只同步一次，保留崩溃恢复和逐版本历史回放语义。节省的毫秒数须通过新旧二进制配对测量。

## 2. 约束与备选方案

已提交的旧块可能跨很多版本复用。把完整视图重新序列化，会让小变更的成本随视图增长。在两个独立文件上省略一次同步，则无法仅靠目录同步保证两个文件的数据都持久化。选用一个物理文件承载多个独立 Arrow IPC 段，每个逻辑块继续单独引用和读取。基表块、表增量、回执及算子检查点继续沿用各自的提交流程。

## 3. 文件与发布

- 每个视图、每次提交至多新增一个这类合并文件。仅将本次新写的结果块和同一视图的输出日志合并。复用旧块的描述符。有序输出保留行顺序。空结果、零行日志以及只需发布单份数据的场景保留各自语义。
- 写入新版本目录，每个段是独立的完整 Arrow IPC 文件。清单用文件名、段偏移、长度和 SHA-256 引用结果或日志段。文件末尾记录物理总长。段的角色由结果块或日志位置确定。读取器校验文件类型、路径、尺寸、区间溢出、各逻辑段原有上限、哈希和预期模式。按范围读取和校验，避免读取旧块时加载整个合并文件。写入逐段进行，限制峰值缓冲；任一段编码失败都不得推进提交。
- 所有段写完后同步合并文件一次，随后持久化清单并按原顺序同步目录、替换和同步 `CURRENT`。仅在此后确认内存候选状态。逻辑结果块及日志分别计数，物理文件及同步次数按实际操作统计，禁止将同一物理文件的字节数重复计入两类段。
- 压缩和垃圾回收按物理文件判断可达性。任何保留版本的结果块、日志或其他合法引用仍然需要一个段时，必须保留整个文件。最后一个引用释放后才能回收。一个存活块可能延长同文件中日志段的保留期，这是减少同步次数的空间代价。

## 4. 初始化与故障恢复

项目尚未发布。从空仓库开始即使用 v3；实验的两套仓库分别用各自二进制从同一份 SQL 和 CSV 初始化。

发布前崩溃时，旧根仍能恢复，未发布的孤立文件随后回收。发布后即使响应丢失，也应能从同一根恢复新版视图和对应的完整日志，带 ID 的事务重试返回原结果。损坏或截断的被引用段必须报告错误，禁止将其当作空结果或空日志。

## 5. 验收条件

1. 从空仓库创建基表和视图，验证每次提交后的全量 SQL、视图结果、逐版本日志和请求重试。覆盖插入、删除、多块部分复用、有序输出、多个视图、相互抵消的变更及检查点。
2. 在合并文件已写而根尚未切换、根已持久化而调用尚未返回两侧注入故障，同时用独立子进程强杀验证。重启后校验正确版本、视图内容、回执和输出历史，继续写入并再验证。覆盖段越界、截断、内容损坏，以及只剩一个段被引用和所有段均不可达时的回收。
3. 使用仓库现有 SQL 检查入口覆盖默认和 Iceberg 配置。对 Q6 单行变更检查视图结果块与日志只有一个物理载体、一次文件同步，普通提交总同步次数预期从 9 减至 8。检查点样本单列。设计通过评审和实现通过测试分别记录。
4. 复用同一份 6,005 行明细、原始 Q6、1 行及 100 行的插入和删除、同种预热、四组配对仓库和发布构建。使用相同适配器交错运行旧版增量、新版增量与无视图全量对照。逐次独立核对金额、模式和受影响行数。报告 DML P50、配对耗时差、带一次读取的总耗时及检查点样本。主要延迟取无埋点运行，另用诊断运行核对同步次数。改善与退化均如实记录。

## 6. 本地 Q6 对照结果

**已验证。** 测试机为 Apple M2 Pro（10 核、16 GiB）、macOS 14.8.9、APFS。两版均由 Rust 1.95.0 使用锁定依赖和 release 优化构建。基线为 `1486d3b`，候选为本文所附实现。两版各自从相同的 SQL 和 6,005 行原始明细初始化仓库。每次插入或删除后读一次结果，全量对照每次重新执行原始 Q6，将结果返回内存。四组独立副本轮换运行四种组合，每组排除第一轮预热。两版返回的列名、类型、可空性、受影响行数和每一次收入均通过校验。所有运行结束后均重新打开并回放保留历史。测试期间暂停了本次任务的后台编译。

96 对计时写入中，有 92 对普通提交。合并前后普通写入的 P50 为 22.41 ms 和 17.86 ms，降幅 20.3%；逐对计算的节省中位数为 3.24 ms。其余 4 对写入均在第 16 次变更落检查点，P50 从 32.10 ms 降至 29.09 ms，样本量不足以估计尾延迟。同步诊断使用单独的构建，在每次实际文件或目录同步成功后记录调用。每版另跑 28 次写入，27 次普通提交的同步次数全部从 9 减为 8，一次检查点提交从 14 减为 13。普通写入的结果块和输出日志合计只同步一个 `view-<id>.pack`。本机这一写一读的负载中，四种变更的总耗时中位数仍以全量路径较低。

输入原始 SQL 的 SHA-256 为 `a0ed1cd7ee4817ab7792f34ce0cbc0d0b1e59ff6c535769852740431ac43b522`。基线和候选计时程序 SHA-256 分别为 `738b95a7e072b9c042057b6e657386f30e62b431c5a2e1e6c0b8faece068513e` 和 `b2b8e3b313a16b0ce1df3547e743d9a3ae891eca60128cebebbbc882c73b4bf2`。对照工具输出各二进制和工作负载的 SHA-256，并保留逐次原始记录。以上测量仅覆盖本地单会话，无法估计目标生产环境的收益。

### 复现配对测量

从仓库根目录执行。基线检出中仅加入同一计时适配器，两套引擎使用独立构建目录。

```sh
RUN=$(mktemp -d)
mkdir "$RUN/before"
git archive 1486d3b | tar -x -C "$RUN/before"
cp optd-incremental-sql/examples/benchmark_q6_write.rs "$RUN/before/optd-incremental-sql/examples/"
python3 optd-incremental-sql/benchmarks/tools/extract_repository_tpch.py
CARGO_INCREMENTAL=0 CARGO_TARGET_DIR="$RUN/build-before" cargo +1.95.0 build \
  --manifest-path "$RUN/before/Cargo.toml" --locked --release -p optd-incremental-sql \
  --example sql_database --example benchmark_q6_write
CARGO_INCREMENTAL=0 CARGO_TARGET_DIR="$RUN/build-after" cargo +1.95.0 build \
  --locked --release -p optd-incremental-sql --example sql_database --example benchmark_q6_write
OLD="$RUN/build-before/release/examples"
NEW="$RUN/build-after/release/examples"
python3 optd-incremental-sql/benchmarks/tools/compare_q6_writes.py "$RUN/results" \
  --old-cli "$OLD/sql_database" --old-driver "$OLD/benchmark_q6_write" \
  --new-cli "$NEW/sql_database" --new-driver "$NEW/benchmark_q6_write"
```
